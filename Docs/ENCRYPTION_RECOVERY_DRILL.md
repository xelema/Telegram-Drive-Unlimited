# Encryption recovery drill

Status: native fixture recovery journeys PASS locally; real-device drill UNRUN. Use expendable test files and a separate backup of the existing encrypted vault before replacing anything. Supporter activation recovery is a separate system and is not changed by this drill.

1. Create/unlock a test vault in Settings → Encryption. Upload a plain control file and protected files with and without protected names, including a Folder Sync file with a nested relative path. Keep original plaintext hashes outside the app. Expected: protected downloads match; the nested path restores correctly. Failure means transfer or metadata placement is not ready.
2. Export a recovery bundle with a distinct strong recovery passphrase. Store the bundle and passphrase separately. Verify it in the current unlocked vault. Expected: verification covers the current master key and all profile keys. Re-export after changing any supported encryption material. The native fixture separately adds a profile key and proves an older bundle reports incomplete coverage; profile creation has no production UI, so that substep is fixture-only. Failure risks losing newer keys.
3. Lock, restart and unlock. Change the vault passphrase using the current passphrase. Try an incorrect current passphrase first. Expected: rejection leaves the existing passphrase and file intact; the correct change preserves protected downloads after restart. Failure means authentication or persistence is unsafe.
4. On a separate private test installation, restore the bundle with the recovery passphrase and a new vault passphrase. When replacing an existing vault, read the replacement warning and confirm deliberately; preserve the original vault backup. Expected: restored identity/profile coverage matches, downloads authenticate, and restart unlocks using the new vault passphrase. Failure blocks release acceptance.
5. Try a wrong recovery passphrase and a truncated bundle. Expected: rejection creates no partial replacement; the prior vault remains usable. Cancel/lock during a derivation. Expected: no late unlock or file commit. Failure is a release blocker.
6. Test an interrupted protected upload larger than 10 MiB and resume after restart with unchanged source and credentials. Expected: it continues the envelope, publishes once and decrypts to the original hash. Change the source in a separate test. Expected: a fresh upload rather than reused ciphertext. Failure risks integrity or nonce reuse.
7. If recovery replacement was mistaken, quit the app and restore the saved original encrypted vault or the newest replacement archive in the private application-data directory. Restart and use its original passphrase. Expected: the original identity and files are recoverable. Do not delete archives until verified. Record the exact paths privately; do not publish secrets in acceptance evidence.

Record OS, installed version, fixture file hashes, each result and any sanitized error in `RELEASE_ACCEPTANCE.md`. Loss of the vault keys and recovery bundle makes vault-only encrypted files unrecoverable. A separate file-passphrase slot still requires its file passphrase. Exporting a bundle is not proof until a restore and authenticated download succeed.
